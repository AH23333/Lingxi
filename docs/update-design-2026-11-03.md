# 检查更新 + 一键自助更新 —— 设计文档

日期：2026-11-03 ｜ 状态：批次 1-2 已落地（检查侧完成），实现批次见 §10 台账

## 0. 目标与非目标

**目标**：用户在设置页点"检查更新"，能发现 GitHub Releases 上的新版本，下载→校验→替换磁盘文件→重新注册，全程只需一次 UAC 确认；失败可回滚，绝不半替换。

**非目标**：
- 不做"免重启热生效"（系统机制不允许，见 §7）；
- 不执行下载包内的任何脚本/可执行文件（安装动作全部由我们自己的代码完成）；
- 不做增量/delta 更新，只做整包替换；
- 不引入第三方网络/JSON/压缩库（零新增依赖：WinHTTP + CNG + 手写最小 JSON + zip 中央目录自校验 + 系统 `tar.exe` 字节解出）。

## 1. 更新源与配置

- 接口：`https://api.github.com/repos/{owner}/{repo}/releases/latest`。
- **仓库地址可配置**：HKCU 设置键 `UpdateRepo`（REG_SZ，形如 `owner/repo`），默认**空**。
  空 = "未配置更新源"，属正常态：UI 如实显示，不发错误弹窗、不写错误状态、不自动重试。
- 自动检查开关：`UpdateAutoCheck`（REG_DWORD，默认 **0=关**）；开启后每天至多自动检查一次，
  上次检查时间记 `UpdateLastCheck`（REG_QWORD，Unix 秒）。
- 将来发布时要做的事（写死在这里，发版契约的一部分）：
  1. 把 `UpdateRepo` 默认文档值写进 README/设置页提示，例如 `your-org/lingxi-ime`；
  2. 打 tag `v<major>.<minor>.<patch>`（与 `common/version.h` 完全一致）；
  3. 按 §2 契约产出三个资产并上传 GitHub Release。

## 2. 发版契约（资产命名与格式）

一次 release 必须包含且仅依赖以下三个资产（名字**逐字符**匹配，大小写敏感）：

| 资产名 | 内容 |
|---|---|
| `LingxiIme-win-x64.zip` | x64 全套：`ImeCore.dll`、`LingxiUI.exe`、`imecheck` 相关件、`data\*.txt` 等运行时件 |
| `LingxiIme-win-x86.zip` | x86 全套：`ImeCore.dll`（32 位）及其 32 位宿主需要的件 |
| `SHA256SUMS.txt` | 两个 zip 的 SHA256 |

**SHA256SUMS.txt 格式**（与 GNU coreutils `sha256sum` 输出兼容，UTF-8 无 BOM，LF 换行）：

```
<64位小写hex>  LingxiIme-win-x64.zip
<64位小写hex>  LingxiIme-win-x86.zip
```

规则：
- 缺任一 zip、缺 SHA256SUMS.txt、或 SHA256SUMS 里缺对应行 → **该版本判不可用**，
  状态显示"发布包不完整"，**绝不降级成"直接装"**；
- zip 内条目：只允许根级相对路径（不含 `/`、`\`、`..`、盘符、`:`、符号链接、加密条目），
  单文件解压后 ≤ 64 MB，整包解压后总大小 ≤ 256 MB，条目名 ≤ 64 字符且不得是
  Windows 保留设备名（CON/NUL/COM1…）、不得以点或空格结尾；
- 版本号规则：语义化 `major.minor.patch`，tag 为 `v` + 版本串；预发布后缀（`-rc1` 等）
  本期**不接受**为可更新版本（见 §3 比较规则）。

## 3. 版本真源与比较

- 真源：`common/version.h`（`LINGXI_VERSION_MAJOR/MINOR/PATCH` + `LINGXI_VERSION_STRING`）。
  DLL、UI、更新逻辑、工装全部从此取，禁止第二处硬编码。构建戳走编译器 `__DATE__ __TIME__`。
- 远端版本取自 release 的 `tag_name`：剥掉前导 `v` 后解析 `X.Y.Z`。
- **语义化数值比较**（三段十进制数，逐段比大小），禁止字符串比较：
  - `1.0` 与 `1.0.0` 等价（缺省段补 0）；
  - 非法版本串（非数字、负数、段数 >3 带预发布后缀）→ 判"版本号无法解析"，不可用态，不更新；
  - 预发布后缀：本期一律拒绝（宁可不更，不可误更）。

## 4. 威胁模型与对策

信任根 = GitHub 账号安全 + HTTPS 传输。以下按攻击路径列：

| # | 攻击路径 | 对策 |
|---|---|---|
| T1 | 中间人替换下载内容 | 仅 HTTPS；下载后**先对整包算 SHA256** 与 `SHA256SUMS.txt` 比对，不匹配整包丢弃，绝不替换、绝不执行 |
| T2 | 把下载重定向到恶意域 | 域名白名单：`api.github.com`、`github.com`、`objects.githubusercontent.com`；WinHTTP 禁用自动重定向，逐跳取 `Location` 并**解析最终 URL 的 host 再校验**，白名单外一律失败 |
| T3 | `SHA256SUMS.txt` 本身被换 | 它随同一 release 经 HTTPS 取回；校验的是"zip ↔ SUMS"绑定。若 release 页整体被篡改，信任根已失守（T1 无法再防，如实声明）。SUMS 解析失败/缺行 = 不可用 |
| T4 | zip-slip（`..\..`、绝对路径、盘符、NTFS ADS `name:`） | 解压前自解析 zip 中央目录，按 §2 条目规则**全量预校验**，违规即整包拒绝；解出目录固定为 `staging\<版本>\`，不由包内容决定 |
| T5 | 符号链接条目指向系统敏感位置 | 中央目录 external attributes 判定，拒绝任何非普通文件条目（目录条目仅允许根级、无名字冲突） |
| T6 | 解压炸弹（高压缩比撑爆磁盘） | 中央目录 uncompressed size 汇总：单文件 ≤64MB、总量 ≤256MB，超限拒绝；下载体积上限 512MB/包；边解边计数，实际写出字节超声明值立即中止 |
| T7 | 执行包内脚本（伪装成安装步骤） | 更新流程**不调用包内任何 exe/psl/cmd**；解包用系统 `tar.exe`（绝对路径 `%SystemRoot%\System32\tar.exe`），注册/替换由 LingxiUI 自身代码完成 |
| T8 | 恶意 release 投毒（账号被盗/仓库转移） | 无法在客户端根治；缓解：UI 明示"来自 <owner>/<repo> release <tag>"让用户可人工识别；文档要求仓库开启 tag 保护/2FA（运维要求，写进发布流程） |
| T9 | 半替换状态（断电/崩溃/文件锁在替换中途发生） | 幂等流程：先全部 rename-aside 成 `.prev-<ts>`，再全部复制新件，**全部成功才算替换完成**；任一步失败把 `.prev-*` 原名改回；自验失败同样回滚（§6） |
| T10 | 提权进程被滥用 | UAC 只拉起我们自己的已签名/本地构建件 `LingxiUI.exe --update-apply <staging>`，参数仅一个受校验的 staging 路径（必须位于本程序 `bin\work\staging\` 之下、名字等于合法版本串），不接受任意路径 |
| T11 | 限流/断网导致 UI 卡死或静默失败 | 全异步（工作线程 + 状态机回调），UI 线程零阻塞；超时（连接 10s/读 30s）、可取消；403/429 → "GitHub 限流，稍后重试"，明确文案 + 手动重试入口 |
| T12 | 校验"成功"被自报冒充（卸载脚本教训 `9e3f5dc`） | 替换后的自验**不采信任何步骤的返回值**：独立跑 `imecheck` + 两侧探针 `--version` + 重算落盘文件 SHA256 与包内哈希比对，三者全过才报成功 |

## 5. 状态机

```
未配置 ──(填 UpdateRepo)──► 空闲
空闲 ──检查──► 检查中 ──┬─► 尚未发布（404/空列表，正常态，可再次检查）
                        ├─► 已是最新（记检查时间）
                        ├─► 发现新版 x.y.z（附 release notes，等用户点更新）
                        └─► 检查失败（断网/限流/解析失败/发布包不完整，附原因，可重试）
发现新版 ──下载──► 下载中（进度） ──┬─► 校验中 ──┬─► 待替换（SHA256 全过）
                                    │             ├─► 校验失败（整包丢弃，回"发现新版"）
                                    │             └─► 下载失败（回"发现新版"，可重试）
                                    └─► 用户取消 ─► 发现新版
待替换 ──UAC──► 替换中 ──► 自验中 ──┬─► 等待重启生效（终态：提示注销/重启宿主）
                                    └─► 回滚中 ─► 更新失败（已恢复旧件，附原因）
```

- "尚未发布任何版本"是**独立正常态**：不发弹窗、不写错误状态、不进失败计数（有专门测试）。
- 进程重启后状态机回到"空闲/上次结果"，绝不自动续跑替换（替换只在用户显式确认后发生）。

## 6. 更新流程（下载 → 校验 → 暂存 → 替换 → 自验 → 回滚）

1. **检查**：GET `releases/latest` → 解析 tag → §3 比较 → 展示版本与 notes。
2. **下载**：按 §2 契约选资产（缺 x86 或缺 SUMS → "发布包不完整"，终止）。
   先取 `SHA256SUMS.txt`，再取两个 zip 到临时目录（`bin\work\download\`），
   边下边限体积/超时，可取消。
3. **校验**：对每个 zip 算 SHA256（CNG），与 SUMS 逐行比对；不匹配 → 整包丢弃 + "校验失败"。
4. **解压**：zip 中央目录预校验（T4/T5/T6）→ `tar.exe` 解到 `bin\work\staging\<版本>\`。
5. **替换**（一次性 UAC 提权，`--update-apply`）：
   - 对 `bin\Debug\` 与 `bin\Debug32\` 的每个目标文件：存在且被锁 → rename-aside
     成 `<name>.prev-<unixts>`（PITFALLS #89）；未锁旧件同样 rename-aside 保留为快照；
   - 复制 staging 新件到两侧目录。**x64 与 x86 两份都换，缺一不可**
     （历史上"漏掉 32 位导致修了但用户摸不到"）；
   - 重新注册 TSF：x64 `HKLM\SOFTWARE\Classes\CLSID` 与 WOW6432Node 两侧
     （复用 `tools\register.cmd` 的注册形态，由提权进程内代码执行等价操作）；
   - 保留**一份上一版本快照**（最近一次成功替换的 `.prev-*` 集合）供回滚与追溯；
   - 幂等：中途任何失败 → 把本轮所有 `.prev-*` 原名改回，删除已复制的新件，状态"更新失败"。
6. **自验**（T12，独立复核）：`imecheck` 通过 + `bin\Debug\LingxiUI.exe --version`
   输出含新版本串 + 两侧 `ImeCore.dll` 的 SHA256 与 staging 内一致；
   任一不过 → 回滚 + 报明确原因。
7. **收尾**：显示"等待重启生效"，给出自查判据：重启后在 `%TEMP%\lingxi-ime.log`
   （需 `LINGXI_LOG=1`）看 `ActivateEx ... ver=<新版本> build=<新构建戳>` 行。

## 7. 为什么必须重启宿主才生效（系统原因）

TSF 的 DLL 由宿主进程（explorer、微信、编辑器、各 WebView2 宿主…）在**进程启动/首次激活输入法时
加载进内存**，镜像被宿主持有：
- 文件替换（改名/覆盖）只改磁盘，不影响已加载镜像——Windows 不允许改写内存映射中的镜像；
- COM class object 在进程内注册后，进程存活期间不会重新 DllGetClassObject；
- 因此更新只能保证"磁盘与注册表是新件"，**生效 = 宿主进程重启**。
- 最彻底的操作是**注销重登或重启系统**（覆盖所有宿主）；只重启单个程序仅对该程序生效。
- 历史坑（project memory）：TSF DLL 被宿主加载后不会因重新编译而自动更新；重启单个程序不够，
  必须注销重登/重启系统才能让新 DLL 被所有宿主加载。UI 结尾必须把这一点讲透，
  并给 §6.7 的日志自查判据，避免用户误判"更新失败"。
